# C1 设计提案：争议与补偿协议

> **本文是设计提案，不是冻结契约，不含任何代码改动，不改动
> `SHOPPING_CONTRACT_VERSION`。** 它描述"如果要做，应该长成什么样、以及哪些
> 部分现在**不能**做"，供后续讨论。
>
> 与 [CONTRACT.md](CONTRACT.md) 一样：本文件描述的一切都是 demo 应用扩展，
> 不是 OCP Catalog 标准的一部分。

---

## 0. 一句话结论

**这套协议没有仲裁者，因此能做的、且只应该做的，是"结构化主张 + 商家预先承诺的自动救济"，
而不是裁判。**

裁判（adjudication）需要一个有权限的第三方来认定事实。本协议没有账户体系、没有第三方权威、
没有可信时间、也没有防篡改日志——**四个信任根一个都不在**。硬做"谁对谁错"，
产出的是错误码换了个名字，而不是争议解决。

但商家**可以预先承诺**："如果你在窗口 W 内、带着证据 E 告诉我情形 X，我自动执行救济 Y。"
这是可机检的、单方允诺的、可自动执行的——它不需要仲裁者，只需要商家愿意被自己的话约束。

---

## 1. 为什么现在不能做裁判：四个缺失的信任根

| 缺失 | 现状 | 后果 |
|---|---|---|
| 账户体系 | `x-dev-caller-id` 是明写的替身（[http.ts](../../packages/shopping-contracts/src/http.ts)） | 无法确定"**谁**在主张"；一个可伪造的 header 不是当事人身份 |
| 第三方权威 | 不存在 | **没有裁决者**；争议无法被判定 |
| 可信时间 | `occurred_at` 来自商家自己的时钟（`ctx.clock`） | 时间戳由被投诉方控制，不能作为中立证据 |
| 防篡改日志 | `purchase_events` 是真源注释里明写的"**应用过程记录**"，未哈希链、未签名（[events.ts](../../packages/merchant-core/src/events.ts)） | 证据由**被投诉方**持有并可修改 |

第四条是最要命的一条：**投诉的对象，同时是证据的保管人。**

---

## 2. 证据现状与强度

先诚实地盘一遍"现在到底有什么能拿上台面"。

| 证据 | 谁持有 | 被投诉方可否伪造 | 强度 |
|---|---|---|---|
| **订单快照**（`items`/`fees`/`total_minor`/`terms_hash`） | 双方各一份 | 商家可改自己的库，**但调用方手里那份是下单响应给的** | **中**：两份可对质 |
| **A 的授权签名**（Ed25519） | **只有 A** | **不能** | **强**：不可伪造、不可否认 |
| 事件流（`quote.created`/`attempt.*`/`payment.*`/`order.*`） | 只有商家 | 可改 | 弱：商家自述的过程记录 |
| 支付引用（`payment_id`） | 只有商家 | 模拟的，无外部可核验性 | 无 |
| 时间戳 | 只有商家 | 可改 | 弱 |

### 2.1 唯一非商家控制的证据，恰好是商家刻意不留的那件

上表里唯一**强**证据是 A 的授权签名。但 [attempt.ts](../../packages/shopping-contracts/src/attempt.ts)
明确写了商家**不存**授权证明，理由是：

> 存下来的证明 = 一张躺在一张被查询端点读的表里的、**可重放的凭证**。

这个取舍是对的——它挡住的是重放攻击。但它同时意味着：**为了保护系统不被重放，
系统销毁了争议最需要的那件证据。**

⇒ 这是本协议的第一课，也是第一个待决设计题（见 §6.2）。

### 2.2 因此：调用方持有的副本是前提，不是锦上添花

如果证据只在商家库里，那么"争议"就等于"相信商家的数据库"——那不叫争议协议。

→ **这正是 `GET /commerce/v1/purchase-attempts/:id/events` 与
`GET /commerce/v1/orders/:id/events` 是争议协议前置条件的原因**：调用方在事发时
就拿到一份自己能留存的记录副本，事后才有对质的基础。没有这一步，后面全是空谈。

## 3. 核心机制：把"谁对"降级为"商家预先承诺了什么"

这不是回避问题，而是**把问题变形（transform）成一个现在就有解的形态**。

| 从 | 到 |
|---|---|
| "这次到底谁违约？" | "本次失败是否落在商家**事先声明会自动救济**的情形清单内？" |
| 需要仲裁者 | 需要一张**可机检的情形表** |
| 事后博弈 | 事前承诺 |

这个模式在本协议里**已经有先例**，不是新发明：

- 报价本身就是商家的预先承诺：一个 `terms_hash`，一个 `expires_at`。
- 授权窗口是 A 的预先承诺：`max_total_minor` 之上我不签。

争议协议只是把同一种"**事先把话说死**"的手法，从价格扩展到**失败**。

## 4. 最小可做设计

### 4.1 主张（Claim）记录

```
Claim {
  claim_id            string        主张自身的 id
  order_id            string        针对哪笔订单
  purchase_attempt_id string        针对哪次尝试（失败路径可能没有 order_id）
  type                ClaimType     见 4.2
  raised_by           string        主张方（当前 = caller id；这正是账户缺失的痛点）
  raised_at           ISO-8601      主张方的时间（不是商家的）
  evidence            EvidenceBundle 见 4.5
  requested_remedy    Remedy        见 4.3
}
```

注意 `raised_at` 由**主张方**提供——商家时钟不可信，所以主张方必须自带时间，
而双方时间不一致本身就要被当作一种需要处理的正常情形，而不是异常。

### 4.2 主张类型与其可机检性

| 类型 | 场景 | 现在能机检吗 |
|---|---|---|
| `not_received` | 用户说未收到货 | **不能**——「收到」是链下事实，协议看不见 |
| `already_fulfilled` | 商家说已发货/已交付 | **部分能**——`fulfillment_status` 与 `order.fulfillment_changed` 是记录，但只是商家自述 |
| `state_inconsistent` | 中断后两端状态不一致 | **能**——`attempt` 终态与 `order` 是否存在可以客观比对，这是最适合先做的一类 |
| `terms_changed` | 价格/条款变了但未告知 | **能**——比 `terms_hash`。商家改了口径，`terms_hash` 就对不上；这是本协议**最强**的一类主张 |

**这张表的读法**：`terms_changed` 与 `state_inconsistent` 可以现在就做到自动化，
因为它们比对的是**协议自己产生的不变量**；`not_received` 与 `already_fulfilled`
依赖链下事实，**永远需要人**。把两者混在一个"争议"框里，是这类协议最常见的失败方式。

### 4.3 自动救济 vs 必须人介入

| 救济 | 能否自动 | 条件 |
|---|---|---|
| `requote`（重出报价） | ✅ | `terms_changed` 且原报价仍在窗口内 |
| `release_hold`（释放库存预留） | ✅ | `state_inconsistent` 且 attempt 终态为 failed |
| `complete_settlement`（补完结算） | ✅ | attempt 停在 `processing` 且 `pending_settlement=1`——**已有**机制（`settlePendingAttempt`），争议协议只是给它一个显式入口 |
| `refund`（退款） | ❌ | 见 §5：支付是模拟的，且 `checkout.ts` 明写不回滚已提交的结算 |
| `compensate`（补偿/违约金） | ❌ | 需要真实资金往来与法律实体 |

前三条是**把已有能力接上一个显式的争议入口**——这跟第 1 项做的是同一件事。

### 4.4 生命周期

```
raised ──► auto_resolved           （落在 4.3 可自动的三类里，机器直接执行）
   │
   ├──► rejected                   （不落在承诺清单内，且商家给出理由码）
   │
   └──► escalated                  （依赖链下事实 ⇒ 必须人介入；协议在此止步）
```

`escalated` 是**诚实的终点**，不是失败。协议明确说"这件事我管不了，请转人工"，
远好过一个假装能判的机器。

### 4.5 证据包（EvidenceBundle）

主张方提交、商家必须接受的最小集合：

- A 侧的**授权签名与载荷**（A 自己持有，商家无法伪造 ⇒ 这是主张里唯一"硬"的部分）
- 商家**当初返回给 A 的订单快照**（A 持有的那份副本）
- 可选：A 持有的两份事件流副本

商家收到后，用 `terms_hash` 比对快照、用 `authorizationSigningBytes` 复算签名。
**这里会立刻撞上 §6.2 的重放问题**——这就是为什么第 2 节要先把它标出来。

## 5. 明确不做（non-goals）

| 不做 | 为什么 |
|---|---|
| **链上锚定 / 可验证凭证** | 没有账户、没有信任根、没有真实当事人。在一个连"你是谁"都答不出的系统里做链上证据，产出的是**表演**而非工程。要做得先有身份层。 |
| **信誉分 / 评级 / SLA** | 需要**跨商家聚合**——那是"协调者"角色的职责，商家（B）在结构上做不到（`trustedMerchants[0]` 只认一个商家）。 |
| **真实退款** | `payment.ts` 是模拟的；且 `checkout.ts` 明写"回滚一次已提交的结算就是退款，而不是我们想要的"。真退款需要真实资金通道 + 法律实体。 |
| **第三方仲裁** | 需要法律实体与管辖约定。**这是法律问题，不是协议问题**——超出本 demo 的表达能力。 |
| **伪造"不可篡改"的说法** | [CONTRACT.md](CONTRACT.md) §11 已写明：未做防篡改验证前**不得**把事件宣传为不可篡改账本。本协议不得绕过这条。 |

## 6. 待决设计题

### 6.1 主张方身份（阻塞项）

`raised_by` 现在只能填 `x-dev-caller-id`——一个可伪造的 header。
**在身份层落地之前，任何"自动救济"都是可被冒领的。** 这是本协议真正的阻塞项：
不是设计做不出来，而是做出来也没有安全的执行者。

### 6.2 非否认证据 vs 重放防护（真实张力）

想保住 A 的签名作为不可否认证据，又不想存一张"可重放凭证"，可能的出路：

- 只存 **`jti` + 签名**，不存完整载荷：签名离开载荷无法被重放（签名不是对"这次请求"的授权，
  而是对"这串字节"的签名，而字节需要商家从自己的库重建）。
- 但商家**能**从库里的 `quote` + `attempt` 重建载荷 ⇒ 重建后签名即可重放。
- ⇒ 所以还要**记录已用 `jti` 并拒重复**（一个一次性票据表）。这样"重放"变成"被拒的重复"，
  签名才可以安全留存。

**这两个方案没被实测过**，属于设计层假设，落地前必须验证方向（尤其"重建载荷后能否复用签名"
这一条要真跑一遍，不能外推）。

### 6.3 双方时间不一致

主张方自带 `raised_at`，商家自带 `occurred_at`。二者不一致是**正常情形**，
不是错误。协议需要一个明确的裁决口径（例如：以商家时间为准记录，
但保留主张方时间作为**声明**，并显式标注二者的差）。

---

## 7. 若要推进，最小的第一步

按"能独立做完 + 低风险 + 不依赖 6.1 那个阻塞项"排序：

1. **把已有能力接上显式争议入口**（对应 §4.3 的前三条）：`state_inconsistent` 与
   `terms_changed` 的机器判定是纯比对，不需要身份层、不需要资金、不碰防篡改问题。
   这是唯一一个**现在就能做完且有意义**的部分。
2. **把 §2 的证据强度表落成代码注释与文档**：让"证据由被投诉方持有"这件事在代码里
   可见，而不是靠口口相传。
3. **6.1 身份层**——不做完这个，第 1 步的自动救济只能用于**自证类**主张
   （如 `state_inconsistent`：同一调用方比对自己那笔尝试的状态），不能用
   于任何涉及第三方利益的救济。
