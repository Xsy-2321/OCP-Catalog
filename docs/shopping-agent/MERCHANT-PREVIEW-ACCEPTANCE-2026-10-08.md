# 用户端与只读商家端：本地预览验收

日期：2026-10-08。沿用现有购物应用与统一 A/B 启动器，新增本地双端入口和商家只读展示。没有提交、推送或部署，没有修改根 `.env`、原演示签名、原数据库或未决购买记录。

## 已交付

| 入口 | 使用方式 |
|---|---|
| 演示门户 `/demo` | 清楚区分用户和商家，标注本地演示、非正式登录 |
| 用户页面 `/` | 保留手动购物、Agent、混合商品、配送、报价确认与恢复；统一启动时显示双端导航 |
| 商家页面 `/merchant` | 商品/库存、订单列表、订单详情；只读刷新和分页 |
| 商家后台 | 沿用已有 B HTTP 服务与 SQLite；没有增加第三套业务服务 |

`bun run shopping:preview` 在 `.codex-tmp/shopping-dual-preview/run-*` 新建独立目录，由系统分配两个空闲端口，打印门户及两个演示入口。恢复已有预览需指定 `SHOPPING_PREVIEW_DATA_DIR`，读取保存的 `preview.json`，继续使用原目录、原端口和原签名。端口占用或必要文件缺失时停止，不切换环境或补造空记录。现有 `shopping:demo` 仍保留原运行参数和数据目录，并增加双端页面；独立 `shopping:start` 不启用商家能力。

完整注册、登录、商品编辑、补库存、接单、退款、店员权限和真实物流均未进入首期范围。

## 数据和访问边界

商品标题、目录价、履约方式及配送费来自 B 已有目录；可用库存与购买预留来自 B 正在使用的 SQLite。订单读取 SQLite 的原 `order_json` 快照，显示确认时的商品和费用，不用现价重新计算历史订单。当前默认目录实际有 5 个商品，页面展示这 5 个，没有另造展示商品或订单。

新增读取能力 `createMerchantDemoReader` 固定当前 merchant/catalog，只执行 SELECT；总览在一次读取快照中提供商品和订单。它不初始化或迁移数据库，不调用购买尝试查询、不触发结算或修复。订单必须通过共同 Order schema、商家范围、行金额、小计、总额和条款 hash 校验；损坏记录返回暂不可用，不编造成功数据。列表隐藏收件人、电话和地址，详情读取原配送资料。

新接口均为 GET：

| 接口 | 内容 |
|---|---|
| `/api/merchant-demo/overview` | 同一时刻的商品/订单总览、来源和检查时间 |
| `/api/merchant-demo/products` | 商品分页，可按关键词读取 |
| `/api/merchant-demo/orders` | 订单分页，按时间及订单号稳定排序 |
| `/api/merchant-demo/orders/:id` | 当前商家与目录内的一笔完整订单 |

默认每页 20 条，最多 50 条。参数白名单拒绝客户端选择其他商家、来源、数据库或用户。商家页面仅调用这些读取接口；错误时清空过期展示，明确提示不可用。

商家入口另发带签名、HttpOnly、SameSite 的一小时演示 cookie，仅用于商家读取接口。普通用户 cookie、前端角色文字和篡改标记不能取得商家读取能力，进入商家页也不会替换用户身份。后台重启后旧商家标记失效，重新打开商家入口取得新标记；用户订单仍属于原用户 cookie。原 Host/Origin/跨站请求检查保留。

这只是本机演示身份：访问本地商家入口即可进入，不能当作正式商家账户或店员权限。服务绑定 `127.0.0.1`，不对局域网或公网开放。

付款显示“模拟已付款”，履约显示“待履约（模拟）”；付款成功不会推导成已送达。商家页没有任何修改库存、接单或付款恢复动作。用户原有授权、预算、原子库存与幂等保护保留。

## 实施中发现与处理

1. 浏览器验收最初假定有 22 个商品，但当前 B 默认目录实际有 5 个。改为核对实际库存记录数量，分页读取真实商品，没有为测试新增商品。
2. 恢复预览时，原签名或数据库同时丢失可能被原启动器当成首次启动。新预览恢复入口先核对数据库、签名和真正的 `agent/sessions/runtime-scope.json`，缺失即停止，并拒绝链接会话目录；6 项启动/恢复测试通过。
3. Windows Bun 1.3.13 在另一个 HTTP 控制处理器内部停止并重建开发模式服务器时，出现残留监听；这不是普通 Ctrl+C 后新进程启动的操作。隔离对照保留了失败记录；启动器明确关闭隐式开发服务器模式。控制处理器内同进程重新开放页面仍出现运行时问题，因此正式浏览器验收采用**等待旧 A/B 进程完整退出，再创建新进程**，并进一步核对页面可访问，而不只检查端口能绑定。这是日常启动/停止方式；不提供进程内热重启功能。
4. 已修复移动端长标题详情溢出及快速关/开详情的旧响应竞态；静态脚本和浏览器核验通过。

## 数据库影响与人工复验

本轮无需迁移，仍为 schema 3；没有新增表、字段或改变交易条款。商品读取复用原目录与库存表，订单读取复用原订单表。新目录的初始化属于原启动器行为；旧库仍保留此前已有升级机制，不能说启动旧库是只读。本轮未启动原数据目录。

可按以下步骤自行复验：

1. 运行 `bun run shopping:preview`，打开终端给出的用户与商家入口。
2. 商家页记录拿铁和美式库存；用户选择各一杯、配送，填写演示收件资料，预算 40 元。
3. 取得 39.90 元报价后先刷新商家：不应有新订单或库存减少。
4. 用户确认购买，再刷新商家：出现一笔订单、两项库存各减一；打开详情核对费用、配送资料，付款与履约分开。
5. 刷新两个页面：订单号保持一致。用 Ctrl+C 停止，按终端打印的恢复命令使用同目录重新启动：订单和库存保留。
6. 在原用户浏览器恢复购买；不要清除用户 cookie，也不要把新演示目录当成旧未知购买失败的证据。
