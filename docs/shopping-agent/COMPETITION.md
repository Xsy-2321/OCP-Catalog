# 一杯之间：应用赛道展示

应用定位：预算受控、逐笔授权、响应丢失后可恢复的咖啡购物助手。

当前展示的是一个独立本地商户。OCP负责读取商户自描述、声明的查询能力和 Resolve 结账入口；购物授权与交易契约是本应用扩展。付款为模拟，不能把订单确认解释成真实咖啡已制作或可取餐。

## 开场说明

建议用一句话描述作品：“Agent 帮我挑咖啡，但预算上限、购买授权和异常恢复由可验证的规则执行。”

主办方已有咖啡购买 Demo，本作品重点展示的是预算、条款绑定和购买结果不确定时的恢复，而不是重复介绍搜索页面。

## 演示准备

1. 用 Bun 1.3.13 安装依赖，将根 `.env.example` 复制为 `.env`，只在后端填 `DEEPSEEK_API_KEY`。
2. `bun run shopping:demo:check` 验证本地运行配置；该命令不验证模型账号余额或远端可用性。
3. `bun run shopping:demo` 同时启动 A/B，打开 http://127.0.0.1:4310。
4. 普通重启沿用数据。要开始新的排练，先正常关闭，再运行 `bun run shopping:demo --new-session`。旧数据、未决订单和密钥不会删除。
   继续该轮时，将 `SHOPPING_DEMO_DATA_DIR` 设为输出的数据目录，再正常启动。
5. 预先在自己的密钥下实测一次 Agent 模式。未填密钥时仍可演示手动搜索，页面会明确显示模型未配置。

## 三段路演

### 正常购买与 Agent 选择

杯数设为2，总预算30元，选择 Agent 模式，输入：“帮两个人挑便宜咖啡，总共不超过30元，到店自取。”

模型会提取需求、调用目录搜索和报价工具。默认数据中两杯美式为19.80元。模型有可能选择其他方案或停止，应以实际返回的候选和报价为准。确认前没有购买尝试；检查最终金额后明确点击购买，订单中分别显示付款与履约状态。

### 预算与确认边界

手动搜索“拿铁”，杯数2，总预算30元。两杯拿铁的目录价格超出预算，不能购买。

再设为1杯、30元，取得拿铁25元的报价。改变表单只是修改新需求草稿，旧报价的确认入口会停用；重新提交或重新取报价后才可以确认。模型只能缩小预算，不能修改商户、币种、杯数上限或代替用户批准购买。

### 响应丢失后的原单恢复

自动浏览器回归 `bun run shopping:browser` 使用独立数据库、测试故障和本地模型协议 fixture，验证：成交响应丢失后，前端暂停新购买；刷新或另一标签页可找回原尝试，恢复同一个订单，不能重复结账。

这个 fixture 用于可重复验收，不是外部模型真实调用证据。故障控制只存在于测试启动器，没有加入正式应用 API。真实模型演示应使用已配置密钥的 `shopping:demo` 页面。

## 原创范围说明

上游 OCP 提供协议、schema、client、CLI 和目录读接口。本作品的应用改动集中在：

- `apps/shopping-agent-web`：需求、Agent 推荐、最终报价、确认、未决交易恢复与状态展示。
- `apps/shopping-agent-api`、`packages/agent-runtime`：模型适配与受约束工具循环、用户确认、签名、会话和未知结果保护。
- `apps/coffee-merchant-api`、`packages/merchant-core`、`packages/shopping-contracts`：本地商户、精确金额、报价/授权契约、库存、模拟支付与持久幂等。
- `tests/shopping-e2e`：真实 HTTP 联合与浏览器验收。

协议客户端、教学示例和协议网站也有缺陷修复，属于工程贡献，不能用整个上游仓库的规模替代本应用创新。
