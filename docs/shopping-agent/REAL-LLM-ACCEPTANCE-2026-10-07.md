**问题清单与复现依据**

1. **F1 / P2：无合格候选时，真实模型可能重复搜索，页面收到通用工具错误。真实调用已观察。**

   输入“一杯脏脏咖啡，到店自取”，预算 30 元。目录确有该商品，库存为零；模型正确解析后调用 `search {}`，然后再次调用同一工具。应用返回 `repeated_tool`，没有正常解释商品已售罄。这次边界拦截有效，没有新订单，但常见缺货需求的体验失败。

   代码依据：[重复工具直接抛错](../../packages/agent-runtime/src/tool-loop.ts#L50)。候选进入模型前已经经过库存、数量和预算筛选，因此空结果不能被模型解读成整个目录没有商品；本轮另一条季节商品输入还出现了“目录里不存在”的无依据说明。

   建议：空候选由后端给出可信的“未找到满足当前条件的可购买商品”终态；需要说明售罄/超预算时提供真实原因。重复动作仍须限制，但给出可操作提示并返回可恢复的搜索状态。

2. **F2 / P2：混合商品需求无法表达，却被执行为一次关键词检索。真实调用已观察。**

   输入“一杯拿铁和一杯美式，两杯总计不超过40元，不要换成同款”。模型提取 `query=拿铁 美式, quantity=2`。商家做整串子串匹配，结果为空，回答“没有可选的拿铁和美式商品”。目录中实际分别有拿铁和美式，两种各一杯合计 34.90 元，但当前订单模型只支持一个商品乘数量。

   代码依据：[需求只含 query/quantity](../../packages/agent-runtime/src/shopping-model.ts#L27)、[单串关键词匹配](../../packages/merchant-core/src/catalog.ts#L208)、[报价只选一个 entry_id](../../packages/agent-runtime/src/shopping-model.ts#L39)。

   建议：当前阶段明确识别并提示“一次仅支持同款多杯”；若扩展混合购买，再实现多商品行、分别取价、合计约束及统一授权，不能只修改搜索词。

3. **F3 / P2：模型会建议不存在的页面功能或对话操作。真实调用已观察。**

   配送输入下，模型建议“在页面把履约方式改为配送”，但界面只有自取，没有配送选择器。低预算场景还建议改履约方式。模型也会说“请告诉我要哪一杯，我再报价”，但 `/api/agent/run` 不接受 session_id 或历史对话，每次重新创建规划；页面没有真正的多轮对话入口。

   代码依据：[履约固定 pickup](../../packages/agent-runtime/src/shopping-model.ts#L157)、[请求只接受 message/quantity/预算](../../packages/agent-runtime/src/shopping-model.ts#L258)、[每轮重新创建会话](../../packages/agent-runtime/src/shopping-model.ts#L247)、[页面控件](../../apps/shopping-agent-web/public/index.html#L20)。

   建议：把“单商户、人民币、仅自取、同款多杯、一次规划”的真实能力显式传给规划器；停止时返回结构化可执行动作，页面只展示存在的操作。配送与对话续接分别作为独立功能实现。

4. **F4 / P2：推荐说明可能与最终报价冲突。确定性本地诊断复现；真实样例尚未出现金额冲突。**

   本地显式 mock 商家拿铁目录 26 元、最终含费 28 元。注入模型 reason“最终含费29元，已符合预算”，应用仍原样输出该说明，与报价 28 元并存。模型只有需求解析、搜索、选品三个响应；最终报价从未传回模型。

   代码依据：[reason 在报价前保存](../../packages/agent-runtime/src/shopping-model.ts#L217)、[模型状态没有 quote](../../packages/agent-runtime/src/shopping-model.ts#L175)、[成功报价后立即停止](../../packages/agent-runtime/src/tool-loop.ts#L28)、[页面原样显示 explanation](../../apps/shopping-agent-web/public/app.js#L126)。

   建议：金额、费用、履约等事实由后端根据已验证报价生成；模型只解释偏好。若要模型归纳最终报价，需要受约束地提供报价并校验输出。

5. **F5 / P2：首选报价失败后，不再尝试其他合格候选。确定性本地诊断复现。**

   本地 mock：30 元预算，特调拿铁目录29元、含费31元；另有经典拿铁含费28元。Agent 首选特调后返回 `failed/budget_exceeded`，只发生3次模型响应，预置下一步改选未执行。同一会话手动改选经典拿铁能进入待确认，证明有可行替代。

   代码依据：[报价错误写为 failed](../../packages/agent-runtime/src/coordinator.ts#L129)、[failed/requote_required 立即终止规划](../../packages/agent-runtime/src/tool-loop.ts#L28)。当前真实 B 自取样例没有额外费用，未用真实服务触发这个含费失败场景。预算保护有效，问题是规划闭环缺失。

   建议：区分可继续选品的报价错误与必须停止的购买/授权错误。对于前者允许有限次数改选，保留整轮期限、重复动作限制和用户确认边界。

6. **F6 / P3：目录扩容后比较范围不完整，且缺少提示。代码核查，当前小目录未触发。**

   [模型只看到前40候选](../../packages/agent-runtime/src/shopping-model.ts#L178)，没有先排序或提示截断；[目录超过50页产生警告](../../packages/agent-runtime/src/ocp-consumer.ts#L136)，[HTTP transport 只取 entries，警告丢失](../../packages/agent-runtime/src/http-transport.ts#L80)。因此不能将“最便宜”推广为任意规模目录的全量比较保证。
